# PII protection part 1: central redaction at the gateway

Every tool result passes through one function, `Upstreams.call_tool`
(`services/gateway/app/upstream.py`), whether it was called by Claude through an
edge, from the dashboard's Tools page, or from Chat. This spec puts a PII filter
there, so no MCP server has to bring its own detection or masking code. Part 2
(asking for and approving access to unmasked fields) gets its own spec.

---

## 0. Agreed requirements

From the conversation:

- **Centralized:** one filter in the gateway covers every server and tool, with
  no per-server code.
- **A switch per gateway:** "PII protection" is set when a gateway is created
  and can be changed later. When it is on, every result through that gateway is
  filtered, for admins and members alike.
- **Regular expressions, no NLP model.** Patterns run on the `regex` package
  (a drop-in for Python's `re` that adds a timeout; see section 4). Presidio plus spaCy is too heavy for v1
  (hundreds of MB of image and RAM, plus warm-up latency). It is the upgrade
  path, described in section 8.
- **Built-in rules plus custom rules:** a fixed set of built-in rules, plus one
  org-wide library of custom rules that admins edit. A gateway with protection
  on applies both.
- **JSON-aware:** rules apply to values at any depth in the JSON payload.
- **The audit log shows the payload the member actually received.**
- **A PII Protection tab** in the dashboard shows the whole global redaction
  schema (built-in and custom rules) and lists every field each WooCommerce
  MCP tool returns, so an admin can tick a field to redact it.
- **Field lists come from each tool's MCP `outputSchema`.** woo-mcp is changed
  to return typed results so it advertises one. A server without output
  schemas still gets the global rules, and its keys can be typed by hand.

Decided in this spec (not stated by the user):

- Each match is replaced by a typed placeholder, `[EMAIL]`, `[PERSON]` and so
  on. There is no partial masking such as `j***@gmail.com`.
- Tool **arguments** are not filtered: Claude has to be able to pass an order id.
- **The filter fails closed:** if redaction throws, the caller gets an error and
  never the unfiltered result.
- **The audit log never holds raw PII.** When protection is off, the member got
  the raw result, but the copy stored in the log is still filtered and marked
  as such. See section 5.

## 1. Data model

```sql
-- Off by default, so existing gateways keep working as they do today.
ALTER TABLE gateways ADD COLUMN IF NOT EXISTS pii_protection BOOLEAN NOT NULL DEFAULT false;

-- The org-wide custom rule library. The built-in rules live in code (pii.py).
CREATE TABLE IF NOT EXISTS pii_rules (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name       TEXT NOT NULL,          -- ^[A-Z][A-Z0-9_]{1,39}$, also the placeholder: [NAME]
    type       TEXT NOT NULL CHECK (type IN ('pattern', 'key', 'field')),
    match      TEXT NOT NULL,          -- a regex (at most 200 chars, compiled on save), a JSON key name, or a field path
    -- Set only for type 'field': the rule applies to this one tool's results.
    server_id  BIGINT REFERENCES servers(id) ON DELETE CASCADE,
    tool       TEXT,                   -- upstream tool name, e.g. get_order
    created_at DOUBLE PRECISION NOT NULL,
    CHECK ((type = 'field') = (server_id IS NOT NULL AND tool IS NOT NULL))
);
-- One field rule per (server, tool, path). Ticking the same field twice is a no-op.
CREATE UNIQUE INDEX IF NOT EXISTS pii_rules_field ON pii_rules (server_id, tool, match) WHERE type = 'field';
-- Pattern and key rules are unique by name; field rules by (server, tool, path) above.
CREATE UNIQUE INDEX IF NOT EXISTS pii_rules_name ON pii_rules (name) WHERE type <> 'field';

-- What got filtered (counts only) and the payload as it was sent back.
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS pii     TEXT;    -- JSON: {"EMAIL": 2, "PERSON": 1}; NULL = nothing matched or not scanned
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS payload TEXT;    -- JSON of the result; see section 5
ALTER TABLE audit_log ADD COLUMN IF NOT EXISTS payload_masked_for_log BOOLEAN NOT NULL DEFAULT false;
```

A `pattern` or `key` rule's name cannot be the same as a built-in rule's name (400).

## 2. Rules

### Built-in rules (in `pii.py`, read-only, always applied when protection is on)

| Name | Type | Match |
|---|---|---|
| `EMAIL` | pattern | `[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}` |
| `SSN` | pattern | `\b\d{3}-\d{2}-\d{4}\b` |
| `CREDIT_CARD` | pattern + check | 13-19 digits, optionally separated by spaces or dashes, **and passing the Luhn check** |
| `PHONE` | pattern | `+`, digits, spaces, dashes, dots and brackets, **10-15 digits**, and never text that starts like a date (`2026-10-11`). Runs after `CREDIT_CARD` and `IP_ADDRESS` |
| `IP_ADDRESS` | pattern | dotted IPv4 with each octet ≤ 255 |
| `PERSON` | key | `customer`, `customer_name`, `first_name`, `last_name`, `full_name`, `billing_name`, `shipping_name` |
| `ADDRESS` | key | `address`, `address_1`, `address_2`, `street`, `postcode`, `zip`, `ship_to`, `billing`, `shipping` |
| `FREE_TEXT` | key | `customer_note` (customer-written free text can contain anything; generic `note`/`notes` are left alone so the demo `notes` server stays usable; an admin can add them as a custom rule) |

Order ids, totals and dates do not match: `PHONE` needs at least 10 digits, and
`CREDIT_CARD` needs a valid Luhn checksum.

### Custom rules (`pii_rules`)

```json
{ "name": "AADHAAR", "type": "pattern", "match": "\\b\\d{4}\\s?\\d{4}\\s?\\d{4}\\b" }
{ "name": "LOYALTY_ID", "type": "key", "match": "loyalty_id" }
```

- `pattern`: compiled with `re.compile` on save. A compile error or a pattern
  over 200 characters is a 400 with the `re` error message.
- `key`: 1-64 characters, matched case-insensitively.
- The placeholder is always `[<name>]`.

### Field rules (`pii_rules` with `type = 'field'`)

A field rule masks **one path in one tool's result**. It is created by ticking a
field in the PII Protection tab (section 6a), not typed by hand.

```json
{ "name": "PERSON", "type": "field", "server_id": 3, "tool": "list_orders", "match": "orders[].customer" }
```

- **Path syntax:** key names joined by `.`. A `[]` after a key means "each
  element of this list". Examples: `customer`, `orders[].customer`,
  `items[].name`. Built from the output schema, so a path is always one the
  tool can actually return.
- **Placeholder:** `name` picks the placeholder. It can be a built-in name
  (`PERSON`, `ADDRESS`, `FREE_TEXT`, `EMAIL`, ...) or any valid custom name,
  and defaults to `REDACTED`. For field rules, `name` does **not** have to be
  unique and **may** reuse a built-in name. (The uniqueness check from
  section 1 applies only to `pattern` and `key` rules. Field rules are unique
  per server, tool and path instead.)
- **Why not just a key rule:** a key rule on `name` would also mask
  `items[].name` (a product name) and every product in `list_products`. A
  field rule touches only the path that was ticked.
- **Applies** to `structured_content`, and to `TextContent` that parses as
  JSON (the same object in text form). If an upstream drops or renames the
  field, the rule matches nothing and the tab shows it as "no longer in
  schema", so it can be unticked.

### Order of application

0. **Field rules** for this server and tool: each ticked path is replaced
   whole by its placeholder.
1. **Key rules.** Any dict entry whose key matches (case-insensitively, at any
   depth) has its whole value replaced by the placeholder, even when the value
   is an object or a list. Its contents are not scanned further.
2. **Pattern rules.** Run on every remaining string value, custom rules first
   and then built-ins, in a fixed order. (An admin's specific pattern wins:
   otherwise PHONE would take `2345 6789 0123` before an AADHAAR rule sees it.) Only the first 100 KB of each string is
   scanned and the rest is replaced with `[TRUNCATED]`. This caps the damage a
   slow, admin-written regex can do.

Numbers, booleans and dict **keys** are never changed.

## 3. The filter: `services/gateway/app/pii.py`

```python
def load_rules(db) -> list[Rule]:
    """Built-ins plus every row in pii_rules, read on each call (one small query)."""

def redact_result(result: CallToolResult, rules, server_id: int, tool: str) -> tuple[CallToolResult, dict[str, int]]:
    """A filtered copy of the result and a count of matches per rule name.
    Field rules apply only when their server_id and tool match."""

def schema_fields(output_schema: dict | None) -> list[dict]:
    """Every leaf path in a JSON Schema: [{path, type, description}]. Follows
    $ref/$defs and array items. No schema: empty list."""
```

`redact_result` handles:

- **`structured_content`**: walked recursively.
- **Each `TextContent`**: `json.loads` it. If that works, walk the parsed value
  and `json.dumps` it back. If not, run the pattern rules over the plain text
  (key rules cannot apply to plain text).
- **Other content types** (images, resources, audio) are dropped and replaced
  with `TextContent("[non-text content removed by PII protection]")`. They
  cannot be scanned, and failing closed beats leaking them.

The function is pure: no I/O and no state, so it is easy to unit-test.

## 4. Flow in `call_tool`

After the upstream answers (or after any error result is built) and **before**
the audit insert:

```
protected = SELECT pii_protection FROM gateways WHERE slug = ?   -- read fresh every call
rules     = load_rules(db)
if protected:
    try:
        with anyio.fail_after(FILTER_TIMEOUT):          # 2 seconds
            result, counts = await anyio.to_thread.run_sync(
                redact_result, result, rules, row and row["id"], tool)  # row None: unknown tool, no field rules
    except TimeoutError:
        log.error(...)                                   # names the server and tool, never the payload
        result = error_result("Result withheld: the PII filter took too long. An admin can check the PII rules.")
        counts = {"FILTER_TIMEOUT": 1}
    except Exception:
        log.exception(...)
        result = error_result("Result withheld: the PII filter failed. An admin can check the gateway log.")
        counts = {"FILTER_ERROR": 1}
```

**A filter failure fails only that one tool call.** The gateway process,
other users' calls, other tools and other servers carry on. The next call to
the same tool tries again.

- **Why the `regex` package, a thread and one deadline:** a custom regex with
  catastrophic backtracking (e.g. `(\w|\w\w)+$`) does not raise an error, it
  just runs for a very long time. Python's `re` holds the GIL for the whole
  match, so even in a worker thread it froze the pod (measured: the event loop
  got 1 tick in 10 s). `regex` with `concurrent=True` releases the GIL, and
  every substitution gets `timeout=` the time left before one shared 2-second
  deadline, so the filter stops itself and its thread ends. `fail_after` is
  only a backstop. That one caller gets the "withheld" error; every other call
  carries on.
- The audit log's masked copy (section 5, protection off) runs under the same
  thread and time limit. If that copy times out, `payload` is `NULL` and `pii`
  is `{"FILTER_TIMEOUT": 1}`. The member still gets the raw result, because
  protection is off for that gateway.

- Error text is filtered too, because upstream errors sometimes echo input
  data. Since redaction happens before the `audit_log.error` text is built, the
  error column is clean as well.
- **A protected gateway lists tools without `outputSchema`.** MCP clients
  check `structuredContent` against it, and a masked value (an `integer` id
  shown as `"[REDACTED]"`, or an object replaced by a key rule) would make the
  client reject the whole result. The dashboard still reads the schemas from
  the health loop's cache.
- Callers do not change: the edge's `/mcp`, `/api/tools/call` and Chat all
  already go through `call_tool`.
- The refusals the gateway writes itself ("Unknown tool", the rate limit, a
  missing credential) contain no upstream data, but they go through the same
  path anyway. That keeps the code to one branch.

## 5. Audit: the payload the member received

Every audit row stores `payload`: `result.model_dump_json()` of the result as it
was **returned to the caller**.

| Gateway protection | Member received | `payload` stored | `payload_masked_for_log` |
|---|---|---|---|
| on | filtered result | that same filtered result | false |
| off | raw result | the result **run through the filter just for the log** | true |
| on, filter failed or timed out | the "withheld" error | that error | false |

- With protection off, the log still never holds raw PII, so the audit table is
  not a second copy of customer data. The dashboard shows a badge on those rows:
  *"Member saw unmasked data; log copy masked."*
- If filtering the log copy itself fails or times out, `payload` is stored as
  `NULL` and `pii` as `{"FILTER_ERROR": 1}` or `{"FILTER_TIMEOUT": 1}`.
- **Size cap:** at most 64 KB per payload. Anything longer is cut off and ends
  with `…[truncated, N bytes]`.
- `pii` holds the counts as JSON, e.g. `{"EMAIL": 1, "PERSON": 1}`, and never
  the values.

### API

| Endpoint | Change |
|---|---|
| `GET /api/audit` | Leaves `payload` out of the list (100 rows × 64 KB is too much); returns `pii` and `payload_masked_for_log` |
| `GET /api/audit/{id}` | New. Admin only. One row including `payload` |

Both are admin-only, like the audit log today.

### 6a. PII Protection tab (admin)

A new sidebar tab, **PII Protection**, with three sections from top to bottom:

1. **Global redaction schema.** One table with every rule that applies to all
   servers: the built-in rules (marked "built-in", read-only) and the custom
   `pattern` and `key` rules (deletable). Columns: name, type, match, example
   placeholder. An **Add rule** form below it takes name, type (pattern or
   key) and match. A bad regex shows the `re` error inline.
2. **Fields by server and tool.** For each enabled server, its tools are
   listed (e.g. `woocommerce → list_orders, get_order, update_order_status,
   list_products, create_product, delete_product`). Each tool expands into its
   field tree from `GET /api/pii-rules/fields`:

   ```
   get_order
     ☐ id               integer
     ☐ number           string
     ☑ customer         string    covered by PERSON (built-in key rule)  🔒
     ☐ items[].name     string
     ☐ payment_method   string
     ☑ customer_note    string    covered by FREE_TEXT                   🔒
     ☑ ship_to          string    ADDRESS  (field rule)  [placeholder ▾]
   ```

   - **Ticked and locked:** a global key rule already matches this field. To
     change that, edit the global schema.
   - **Ticking a free field** creates a field rule for that server, tool and
     path. A placeholder dropdown lists the built-in names plus
     `REDACTED` (the default). Unticking deletes the rule.
   - **Stale rules** (the path is gone from the schema) appear under the tool,
     struck through, with a remove button.
   - **No output schema:** "This tool doesn't describe its output. Global
     rules still apply; add a key rule above for any other field."
3. **Test.** Pick a server and tool (optional), paste JSON, and see the
   filtered result and the counts (`POST /api/pii-rules/test`).

Changes take effect on the next tool call on every pod. The rules are read
fresh, as policies are.

### 6b. woo-mcp: advertise output schemas

`services/woo-mcp/app/server.py` stops returning `dict[str, Any]` and returns
Pydantic models, so the MCP SDK publishes an `outputSchema` for each tool and
sends `structured_content`. The fields and values do not change.

| Model | Fields |
|---|---|
| `Product` | `id, name, price, status, stock_status, sku, url` |
| `LineItem` | `product_id, name, quantity, total` |
| `OrderSummary` | `id, number, status, total, currency, created_utc, customer, items: list[LineItem]` |
| `Order(OrderSummary)` | `+ payment_method, customer_note, ship_to` |
| `ProductList` | `count, products: list[Product]` |
| `OrderList` | `count, orders: list[OrderSummary]` |

Each tool's return type becomes the matching model (`get_order` → `Order`,
`list_orders` → `OrderList`, ...). Each field gets a short `description`,
which the tab shows. `_product` and `_order` build the models in place of the
dicts. woo-mcp's chart version is bumped so the store operator rolls it out.

The gateway's health loop already caches `Tool` objects, `output_schema`
included, so nothing on the gateway side fetches schemas.

## 7. Testing

Unit tests (`tests/test_pii.py`, no database needed):

- Each built-in pattern matches its example. A Luhn-failing 16-digit number, an
  order id (`2042`), a total (`"149.00"`) and an ISO date are left unchanged.
- Key rules: `customer` at the top level, `billing.first_name` two levels down,
  a key whose value is a dict, and case-insensitive `Customer`.
- A `TextContent` holding JSON is walked and stays valid JSON. A plain-text
  `TextContent` gets the pattern rules.
- Non-text content is replaced.
- Custom pattern and custom key rules apply. The counts are right.
- A string over 100 KB is truncated.
- Field rules: `orders[].customer` masks every order's customer and leaves
  `orders[].items[].name` alone; a rule for another tool or server does
  nothing; a path missing from the payload does nothing.
- `schema_fields`: a woo `Order` schema (with `$defs`/`$ref` and an array of
  `LineItem`) gives `items[].name` and the other leaf paths; `None` gives `[]`.

woo-mcp tests: each tool's listed `outputSchema` has the fields in the 6b
table, and `get_order` returns `structured_content` with the same values as
before.

Gateway tests (Postgres, as in earlier parts):

- An edge with protection on calls a fake upstream returning a woo-style order,
  and the caller gets `customer: "[PERSON]"` and `[EMAIL]` in `customer_note`.
  The same call with protection off returns the raw values.
- The audit row: `pii` counts are set and `payload` equals what was returned.
  With protection off, `payload` is masked and `payload_masked_for_log` is true.
  No raw email appears anywhere in the row.
- When `redact_result` is patched to raise, the caller gets the "withheld"
  error and the audit row has `FILTER_ERROR`.
- When `redact_result` is patched to sleep past `FILTER_TIMEOUT`, the caller
  gets the "took too long" error with `FILTER_TIMEOUT`, and a second call made
  at the same time to a server without protection still answers at once (the
  event loop was not blocked).
- Rule API: member 403; bad regex 400; built-in name 400; duplicate 409; a new
  rule applies on the very next call. `/api/pii-rules/test` stores nothing.
- Field rule API: a field rule without server and tool is 400; the same
  server, tool and path twice is 409; deleting the server deletes its field
  rules. `GET /api/pii-rules/fields` marks a field covered by a key rule as
  `covered_by`, a ticked field with its `rule`, and a field rule whose path left
  the schema under `stale`.
- `PUT /api/gateways/{slug}/pii` applies on the next call.
- `GET /api/audit` leaves out `payload`; `GET /api/audit/{id}` includes it.

Dashboard: `npm run build`, then checked by hand on the k3d cluster against
`shop1__get_order`.

## 8. Scaling up: Presidio (the proposal for larger installs)

Regex plus key rules work well when the payloads are known and fairly flat.
They break down when:

- names, addresses or other PII sit inside free text,
- there are dozens of servers with deep schemas nobody has catalogued,
- the PII is region-specific (passport numbers, national IDs) or the text is
  not in English.

The upgrade keeps the same choke point and the same `redact_result` contract:

- Run **Microsoft Presidio** (`presidio-analyzer` and `presidio-anonymizer` with
  a spaCy model) as a **separate service** next to the gateway, not inside it,
  so the gateway image and memory stay small and the model loads once.
- `redact_result` keeps the key rules locally (cheap, exact), then sends the
  string values to Presidio in one batched request per result. Presidio's NER
  finds `PERSON` and `LOCATION` in free text; its pattern recognizers with
  context and checksums replace our regexes; the custom rules become Presidio
  ad-hoc recognizers.
- Same fail-closed rule: if Presidio is down or slow (call timeout), the result
  is withheld and never passed through.
- What it costs: a few hundred MB per Presidio pod, and tens of ms added to each
  call depending on payload size. That is acceptable for a support workflow,
  and it is why it is an opt-in deployment rather than the default.

Even with Presidio, automatic detection is a **safety net, not a guarantee**.
Picking only the fields a tool needs at the source (as woo-mcp already does: no
email, phone or street) and authorization remain the first line of defense.

## 9. Out of scope (part 2 and later)

- **Access requests:** a member asks to reveal specific fields of a specific
  record with a reason; an admin approves or rejects it in the dashboard; the
  approval is scoped, expires, and is audited. Its own spec.
- Partial masking (`j***@gmail.com`) and consistent tokens (the same email gives
  the same `[EMAIL_1]` within a session).
- Filtering tool arguments, tool descriptions, or Chat's model messages.
- Per-gateway selection of custom rules; per-server `pattern`/`key` rules (field rules are the per-tool mechanism).
- An audit payload retention policy (the rows grow with call volume, 64 KB
  each at most).
