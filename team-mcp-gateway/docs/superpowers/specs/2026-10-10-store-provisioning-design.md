# Store provisioning + member access: design

Date: 2026-10-10. Status: draft for review.

Bonus section of the assignment: turn the single store into a store
provisioning platform, driven from the existing dashboard, with every new store
connected to the gateway automatically. Built in two parts; part 2 depends on part 1.

---

## 0. Agreed requirements

From the conversation:

- **Who provisions:** admins only. At most **3 stores per admin**.
- **Three templates** an admin picks from:
  - `catalog-a`: 300 products across categories A (Electronics, Books, Home & Kitchen, Toys, Office).
  - `catalog-b`: 300 products across categories B (Fashion, Sports, Beauty, Grocery, Garden).
  - `blank`: 3 basic products (the current Mercora set: chai, coffee, tumbler).
  Catalogs are **generated by a script with a fixed seed**: same products every deploy, no images.
- **Deleting an admin deletes everything they own**: their stores (namespace,
  volumes, Secrets) and the stores' gateway registrations.
- **Member access:** a new member sees **no** servers. When an admin adds or
  edits a member, they pick the servers that member may use (whole server, no
  per-tool picking). Admins see every server. Admins can already revoke any key.
- **Provisioning component:** a kopf operator watching a `Store` custom resource
  (the Factory pattern), installing the existing `charts/store` (Bitnami
  WordPress + setup Job) and `charts/woo-mcp` with Helm.
- Everything else as in the assignment: one namespace per store, own DB /
  Secrets / PVCs / Ingress host, automatic MCP registration with store-prefixed
  tool names, clean teardown, NetworkPolicy isolation, ResourceQuota + LimitRange,
  provisioning timeout, safe retry, recovery after an operator restart.

Assumptions (not stated, chosen here):

- Each template also seeds a few **orders dated the provisioning day**
  (`catalog-a`: 12, `catalog-b`: 7, `blank`: 2), so "compare today's orders"
  has data on the day the stores are created.
- Store names are **global**, not per admin: `shop1` is one store cluster-wide.
  The store name is the gateway server name and the tool prefix (`shop1__list_orders`).
- No TLS, no plans/sizes, no self-signup (all dropped from the Factory).

**Acceptance test** (from the assignment): an admin creates a `catalog-a` and a
`catalog-b` store; the chat agent compares today's orders across both; the admin
deletes one; its tools are gone from the gateway and its namespace, PVCs and
Secrets are gone from the cluster.

## Part 1: member access (gateway + dashboard)

### Data

New table, foreign keys cascade so deleting a user or a server drops its grants:

```sql
CREATE TABLE user_servers (
    user_id   INTEGER NOT NULL REFERENCES users(id)   ON DELETE CASCADE,
    server_id INTEGER NOT NULL REFERENCES servers(id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, server_id)
);
```

Migration in `db.connect`: if the table does not exist yet, create it and grant
every existing server to every existing member, so nothing breaks on upgrade.

### Enforcement: one place

`Upstreams.list_tools(user)` and `Upstreams.call_tool(user, ...)` filter by
grants: admins see all enabled servers; members only granted ones. A call to a
server the member is not granted returns the same "Unknown tool" error as a
non-existent tool (does not reveal it exists) and is audited.

Callers updated to pass the user: `/mcp` `on_list_tools` (`ctx.request.state.user`),
`GET /api/tools`, `chat.py`. `GET /api/servers` returns only granted servers to members.

### API

| Method | Path | Change |
|---|---|---|
| GET | `/api/users` | each user gains `server_ids` |
| POST | `/api/users` | accepts optional `server_ids` |
| PUT | `/api/users/{id}/servers` | **new**, admin: replace a member's grants `{server_ids: [...]}` |
| DELETE | `/api/users/{id}` | **new**, admin: delete a user. Refuses self and the last admin. If the user is an admin, first deletes their Store resources (part 2); then the row (keys, sessions, grants cascade). Audit rows keep the username. |

### Dashboard

**Members** page (`Admin.jsx`): server checkboxes in the add-member form; a
per-member "Access" editor (same checkboxes) and a Delete button with a confirm
that names what goes with it ("bob's 2 stores will be deleted"). Admin rows show
"all servers".

## Part 2: store provisioning

### Components

```
Dashboard "Stores" tab (admins)
   │ POST/GET/DELETE /api/stores
   ▼
gateway ── creates/lists/deletes Store CRs in namespace mercora (Role: stores only)
                                   │ watched by
                                   ▼
store-operator (kopf, Deployment in mercora, ClusterRole)
   1. namespace store-<name> + ResourceQuota + LimitRange + NetworkPolicies
   2. Secret woo-mcp-credentials (generated once, reused on retry)
   3. helm upgrade --install store  charts/store   (template=<t>, host <name>.localhost)
      helm upgrade --install woo-mcp charts/woo-mcp
   4. timer: Ready when WordPress, setup Job and woo-mcp are all ready
      → upsert gateway server "<name>" (bearer = MCP_AUTH_TOKEN) via gateway API
   delete (finalizer): delete gateway server "<name>" → delete namespace
```

### Store custom resource

`stores.mcpgateway.example.com/v1`, kind `Store`, namespaced in `mercora`,
status subresource. Object name = store name.

- `metadata.labels["mcpgateway.example.com/owner-id"]`: owner's user id.
- `spec`: `template` (`catalog-a|catalog-b|blank`, required), `owner` (username, display only).
- `status`: `phase` (`Provisioning|Ready|Failed`), `message` (reason on Failed,
  current step while Provisioning), `url` (`http://<name>.localhost`), `readyAt`.

Created time = `metadata.creationTimestamp`.

### Gateway: `/api/stores` (admin only)

| Method | Path | Does |
|---|---|---|
| GET | `/api/stores` | Store CRs: name, template, owner, phase, message, url, created. Admins see all stores; the Delete button shows only on their own. |
| POST | `/api/stores` `{name, template}` | Validates name `^[a-z][a-z0-9-]{1,19}$` (short so `<name>__<tool>` stays ≤ 64 chars for the chat agent) and not already a server name; counts the caller's CRs (any phase) and refuses a 4th; creates the CR. **Safe to retry:** if a CR with that name already exists for the same owner and template, return it (200) instead of 409. |
| DELETE | `/api/stores/{name}` | Owner only (404 otherwise): deletes the CR; the operator's finalizer does the teardown. |

Kubernetes access: a small client using the pod's ServiceAccount token (in-cluster)
with a Role limited to `stores` in `mercora`. Not running in a cluster (tests,
local dev) → `/api/stores` returns 503 "store provisioning is not configured",
like the chat endpoint without a key. Tests swap in a fake with the same three methods.

### Operator (port of the Factory's `operator.py`, trimmed)

Kept from the Factory: kopf handlers, `helm upgrade --install` with values in a
JSON file and **no `--wait`**, rollback-once on a release stuck "pending",
409/404-tolerant creates/deletes, status timer that gates Ready on real
readiness, drift-repair timer for NetworkPolicies/quota, the gotchas list.

Dropped: Tenant CRD and handlers, auth, plans, `_recompute_quota`, cert-manager,
IngressRoutes, per-resource cleanup in delete.

**`on_store_created`**
1. Cap re-check: list the owner's Stores sorted by creation time; if this one
   is 4th or later → `Failed`, "store limit (3) reached". Catches two
   simultaneous POSTs that both passed the gateway check.
2. Create namespace `store-<name>` (labels: owner-id, `mcpgateway.example.com/store=<name>`),
   ResourceQuota, LimitRange, NetworkPolicies.
3. Secret `woo-mcp-credentials` with `WOO_CONSUMER_KEY` (`ck_` + 40 hex),
   `WOO_CONSUMER_SECRET` (`cs_` + 40 hex), `MCP_AUTH_TOKEN`: **created only if
   absent**, so a retry never changes the key (fixes the stale-key problem seen
   with the current store).
4. `helm upgrade --install store charts/store -n store-<name>` with
   `setup.template=<t>`, `setup.hook=false`, ingress host `<name>.localhost`,
   Bitnami NetworkPolicies off, PVCs 1Gi each.
5. `helm upgrade --install woo-mcp charts/woo-mcp -n store-<name>` with
   `store.internalUrl=http://store-wordpress.store-<name>.svc.cluster.local`,
   `store.publicUrl=http://<name>.localhost`, `networkPolicy.allowFromNamespace=mercora`.
6. Status `Provisioning`, message "installing".

Errors in steps 2–5 raise `kopf.TemporaryError` (kopf retries with backoff);
after 3 attempts → `Failed` with the helm/API error as `message`.

**`reconcile_store` timer (every 15 s, while Provisioning)**
- Ready when: WordPress Deployment has a ready replica **and** Job `store-store-setup`
  succeeded **and** woo-mcp Deployment ready. Then upsert the gateway server
  (GET `/api/servers`, find by name → PATCH, else POST), set `Ready`, `readyAt`.
- Message shows the step it waits on ("waiting for setup job"), for the dashboard.
- **Timeout:** if now − creationTimestamp > 15 min → `Failed`,
  "timed out waiting for <step>". Measured from creation, so an operator restart
  does not reset it.
- Setup Job failed (backoffLimit exhausted) → `Failed`, "setup job failed: see
  `kubectl logs job/store-store-setup -n store-<name>`".

**`on_store_deleted` (kopf finalizer)**
1. Delete gateway server `<name>` (404 = already gone; grants cascade).
2. Delete namespace `store-<name>` (takes Helm releases' objects, PVCs, Secrets).
3. Wait until the namespace is gone (`TemporaryError` while Terminating), so
   re-creating a store with the same name never hits a Terminating namespace.

**Recovery.** Every create step is idempotent, so when the operator restarts
mid-provisioning kopf re-runs the handler from the top and it converges; the
timer resumes; the timeout still counts from creation. Result: the store
completes or ends `Failed` with a reason. A `Failed` store keeps its namespace
for debugging until the admin deletes it.

**Gateway credential.** The operator calls the gateway with an admin API key
from Secret `store-operator-gateway` (key `GATEWAY_API_KEY`), created once at
install. One-time setup step, not per store.

### Per-store guardrails

ResourceQuota `store-quota`: `requests.cpu: 1`, `requests.memory: 1.5Gi`,
`limits.memory: 3Gi`, `requests.storage: 3Gi`, `persistentvolumeclaims: 2`,
`pods: 10`. (WordPress 250m/512Mi, MariaDB, setup Job 100m/256Mi, woo-mcp
50m/96Mi, plus slack for a rolling update.)

LimitRange `store-limits`: default container request 50m/64Mi, default limit
512Mi, max per container 1Gi memory.

Cap: 3 stores per admin (gateway + operator). Timeout: 15 min.

### Isolation (NetworkPolicies in each `store-<name>`)

Bitnami's own policies are turned off (its WordPress policy allows all ingress,
and allows are additive, so it would undo ours). Ours:

| Policy | Effect |
|---|---|
| `default-deny` | all pods: no ingress, no egress |
| `allow-dns` | all pods → kube-system :53 |
| `wordpress-ingress` | WordPress ← Traefik (kube-system), ← woo-mcp and setup Job in this namespace |
| `wordpress-egress` | WordPress and setup Job → MariaDB :3306 in this namespace; → internet :80/:443 outside the pod/service CIDRs (plugin download) |
| `mariadb-ingress` | MariaDB ← WordPress and setup Job in this namespace only |
| `woo-mcp-ingress` | woo-mcp ← pods `app.kubernetes.io/name=gateway` in `mercora` only (existing chart policy) |
| `woo-mcp-egress` | woo-mcp → WordPress :8080 in this namespace only |

Demo: from `shop1`'s woo-mcp pod, request `shop2`'s WordPress and MariaDB →
connection times out; its own WordPress → 200. (k3s enforces NetworkPolicy with
its built-in kube-router controller.)

### Chart changes

- `charts/store`:
  - new `setup.template` (default `blank`) and `setup.hook` (default `true`,
    keeps today's Mercora behaviour; the operator passes `false` so the Job is
    a plain Job and `helm` returns at once).
  - new `files/seed.php`: one `wp eval-file` run creates categories, products
    and today's orders for the chosen template, using `mt_srand(<fixed seed>)`.
    `blank` reads the existing `setup.products` list. Runs only when the store
    has no products (as today), so re-runs never duplicate.
  - `setup-woo.sh`: the per-product `wp wc product create` loop (about 1–2 s per
    product, too slow for 300) is replaced by the `seed.php` call.
- `charts/woo-mcp`: add an egress policy (WordPress only + DNS).
- `charts/gateway`: ServiceAccount + Role (`stores` in its namespace),
  `automountServiceAccountToken: true`, env `STORES_ENABLED=true`.
- **New** `charts/store-operator`: CRD (in `crds/`), ServiceAccount,
  ClusterRole/Binding, Deployment (1 replica). Image bundles Python + kopf +
  kubernetes client + `helm` + `charts/store` (with the vendored Bitnami tgz) +
  `charts/woo-mcp`.

### Dashboard: Stores tab (admins)

- Form: store name + template picker (three cards: "Catalog A, 300 products: …",
  "Catalog B, 300 products: …", "Blank, 3 products"), Create. Shows "n/3 used";
  Create disabled at 3.
- List: a card per store with status dot (Provisioning / Ready / Failed), name,
  template, owner, URL link (when Ready), created time, message (step or failure
  reason), Delete (own stores, with confirm). Polls every 3 s, like Servers.
- Several stores can be created back to back; each provisions independently.

## Error handling summary

| Case | Result |
|---|---|
| 4th store | 400 from gateway; operator also fails a racing 4th with "store limit (3) reached" |
| name taken by a server or another owner's store | 409 |
| POST retried with same name/owner/template | 200, existing store |
| helm/API error | retried by kopf ×3, then `Failed` + error text |
| setup Job fails | `Failed` + where to read the logs |
| not Ready in 15 min | `Failed` + step it waited on |
| operator restarts mid-provisioning | handler re-runs idempotently; completes or times out with a reason |
| delete while Provisioning | allowed (no `--wait` anywhere), finalizer tears down |
| delete admin with stores | their Store CRs deleted first, then the user |
| gateway not in a cluster | `/api/stores` 503, rest of the gateway unaffected |

## Testing

- **Gateway (pytest, existing style):** grants filter `list_tools`/`call_tool`/
  `/api/servers` for members, admins see all; migration grants existing servers
  to existing members; `PUT /api/users/{id}/servers`; delete user (self and last
  admin refused, owned stores deleted via the fake); `/api/stores` validation,
  cap, idempotent retry, owner-only delete, 503 when not configured.
- **Operator (pytest):** pure functions only: manifests for quota, LimitRange,
  NetworkPolicies; Helm values per template; cap ordering; timeout decision.
- **seed.php:** run in the setup Job; checked live by `list_products` counts
  (300 / 300 / 3) and category names.
- **Live acceptance (k3d `store-check`)**, scripted as a checklist in the README:
  1. create `shop1` (catalog-a) and `shop2` (catalog-b) at the same time; both reach Ready.
  2. chat: "compare today's orders in shop1 and shop2" → calls `shop1__list_orders`
     and `shop2__list_orders`.
  3. isolation: from shop1's woo-mcp pod, shop2's WordPress/MariaDB time out.
  4. member bob granted only `shop1` sees only `shop1__*` tools.
  5. kill the operator pod while a store is Provisioning; it still ends Ready (or Failed with a reason).
  6. delete `shop2` → no `shop2__*` tools, `kubectl get ns store-shop2` NotFound, no PVCs/Secrets.
  7. delete an admin who owns a store → its namespace and server are gone.

## Out of scope

Per-tool grants, plans/sizes, TLS, product images, store upgrades/template
change after creation, more than one gateway replica, a store admin password
shown in the dashboard (it stays in the Bitnami Secret in the store namespace).
