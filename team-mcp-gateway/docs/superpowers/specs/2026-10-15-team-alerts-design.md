# Team alerts: design

## Goal

Tell a team that something it must act on has happened. An admin sets a rule
on a team: "alert this team when tool X succeeds". When any member's call of X
succeeds (a direct call, or an approved run), the gateway stores one alert for
that team. Every member of the team sees it on the **Alerts** tab and through
their AI agent; whoever handles it marks it done, and the whole team sees who.

First use, restock planning (`2026-10-15-restock-planning-design.md`): rule
"alert `store-operators` when `woo__create_restock_plan` succeeds". The
finance member's plan is approved, the store records PO #7, and the store
operators get:

```
PO ordered · woo__create_restock_plan on prod
Fresh Deodorant 150ml (#20): PO #7: 279 x 110.00
Green Tea 100 Bags (#31):    PO #7: 134 x 120.00
requested by priya (finance) · approved by admin · 2 min ago      [Mark done]
```

The feature is generic: nothing in it knows about restock. The same rule can
alert marketing when `create_cart_offers` runs.

## Out of scope (v1)

Email, Slack or webhooks; per-member read/unread state (the badge counts open
alerts); closing an alert automatically from another tool call (the operator
marks it done); alerting on failed calls or on approval decisions (the
requester already gets those from `gateway__wait_for_approval`); alert
retention limits.

## One Alerts tab for everyone

Today the Alerts tab is admin-only and shows approval requests. It becomes
visible to every signed-in user (revised 2026-10-16 at the user's request,
dashboard 0.9.1–0.9.2):

- **Admins:** the approval requests section only, as before.
- **Members:** **Team alerts** for the teams they are in now (leaving a team
  hides its alerts), open and done together, newest first, reloaded every 30 s.
- Each alert card: title, tool and gateway, the per-item lines, who requested,
  who approved (when it was an approved run), when, and "done by ravi, 10:42"
  once done. **No Mark done button:** an alert becomes done only through the
  member's agent (`gateway__mark_team_alert_done`), after it handled the work.
- **Badge:** admins = pending approvals; members = open alerts of their teams.

The gateway API is unchanged (admins may still read every team's alerts, and
`POST /api/alerts/{id}/done` still exists); the dashboard just does not use
those parts.

## Pieces

### 1. Tables (`services/gateway/app/db.py`)

```sql
-- Which tool calls alert which team. Same key as team_tools, and like it,
-- belongs to an attachment: detaching the server deletes the rule.
CREATE TABLE IF NOT EXISTS team_alert_rules (
    team_id    BIGINT NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
    gateway_id BIGINT NOT NULL,
    server_id  BIGINT NOT NULL,
    tool       TEXT NOT NULL,
    PRIMARY KEY (team_id, gateway_id, server_id, tool),
    FOREIGN KEY (gateway_id, server_id) REFERENCES gateway_servers (gateway_id, server_id) ON DELETE CASCADE
);
CREATE TABLE IF NOT EXISTS team_alerts (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    team_id      BIGINT NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
    gateway      TEXT NOT NULL,               -- slug, as in audit_log
    tool         TEXT NOT NULL,               -- full <server>__<tool> name
    title        TEXT NOT NULL,
    lines        TEXT NOT NULL,               -- JSON list of strings, at most 50
    requested_by BIGINT REFERENCES users(id) ON DELETE SET NULL,
    approval_id  BIGINT,                      -- set when the call was an approved run
    audit_id     BIGINT NOT NULL,
    created_at   DOUBLE PRECISION NOT NULL,
    done_by      BIGINT REFERENCES users(id) ON DELETE SET NULL,
    done_at      DOUBLE PRECISION
);
CREATE INDEX IF NOT EXISTS team_alerts_open ON team_alerts (team_id, done_at);
```

### 2. Trigger (`services/gateway/app/alerts.py`, called from `Upstreams.call_tool`)

At the end of `call_tool`, after the audit row is updated, when the result is
not an error and the call was not a built-in `gateway__` tool:

- Find rules for this gateway, server and tool. None: stop (one indexed query;
  the common case).
- **Content comes from the PII-masked copy** (`logged` in `call_tool`), never
  the caller's unmasked result: a team alert is read by people other than the
  caller.
- **Lines:** when the structured result has a `results` list (the bulk shape,
  `BulkResult`), one line per item with `ok: true`:
  `"<name from the call's items, if any> (#<id>): <detail>"`; items that failed
  are summed as one last line, `"2 items refused"`. When every item failed, no
  alert. Otherwise the result's text, first 500 characters, as one line.
- **Title:** the tool's MCP `title` annotation when the upstream gave one
  (e.g. "Create restock plan"), else the tool name.
- One row per matching team. **Never fails the call:** an exception is logged
  and swallowed; the caller gets their result either way.

### 3. API (`services/gateway/app/alerts.py`, mounted in `main.py`)

- `GET /api/alerts?status=open|done|all` → newest first, at most 200:
  `{id, team, gateway, tool, title, lines, requested_by, approved_by,
  created_at, done_by, done_at}`. Members: their current teams only. Admins: all.
- `GET /api/alerts/count` → `{"open": n}` for the caller's view.
- `POST /api/alerts/{id}/done` → caller must be in the alert's team, or admin.
  Already done: 409 "already done by ravi". Not visible to the caller: 404.
- `PUT /api/teams/{id}/gateways/{slug}/alert-rules` (admin), body
  `{"rules": [{server_id, tool}]}`: replaces the team's rules on that gateway,
  like the team's tools and budgets. A rule may name only a server attached to
  that gateway (same check as team tools); the tool need not be one the team
  itself may call. `GET /api/teams` returns each team's `alert_rules` per
  gateway, next to `policies` and `budgets`.

### 4. Built-in MCP tools (agents see alerts too)

Offered to every user on every gateway, next to the approval tools:

- `gateway__list_team_alerts(status: "open" | "done" | "all" = "open")` →
  the same rows as the API, for the caller's teams (read-only).
- `gateway__mark_team_alert_done(alert_id)` → as the API; for "the delivery
  is in, mark it done".

Neither counts against write budgets (built-ins are not budgeted today).

### 5. Dashboard

- `App.jsx`: Alerts no longer `admin: true`; the badge uses the new count
  (admins add pending approvals).
- `Alerts.jsx`: approvals section only for admins; a Team alerts section
  for everyone, with the Open/Done/All filter and Mark done.
- `Teams.jsx`: per team, "Alert this team when these tools succeed", the same
  gateway/server/tool picker as the team's tools.

## Errors

- Rule for a tool later detached from the gateway: deleted with the
  attachment (FK cascade), like team tools.
- Team deleted: its rules and alerts go with it.
- Two members click Mark done at once: `UPDATE … WHERE done_at IS NULL`;
  the second gets 409 with who did it.
- A result with PII on a protected gateway: the alert holds the masked
  text, the same as the audit log.

## Testing

Gateway tests, Postgres on 5433 (`TEST_DATABASE_URL`), in a new
`tests/test_alerts.py` using the existing fixtures and demo upstream:

- rule + successful call → one alert per matching team with the ok items'
  lines; no rule → none; all items failed → none; an error result → none.
- approved run → alert with `approval_id`, and `approved_by` in the API.
- member sees only their teams' alerts; admin sees all; leaving the team
  hides them.
- mark done: team member ok; outsider 404; twice → 409 naming the first.
- masked content: a PII rule on the tool's field → the alert holds the mask.
- built-in tools: list and mark done through MCP.
- rules API: rejects a tool not attached to the gateway; detaching deletes it.

Manual: the restock demo (restock spec, demo steps).
