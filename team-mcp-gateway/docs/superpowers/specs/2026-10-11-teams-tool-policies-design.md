# Gateways part 2: teams and tool-level policies

Part 2 of the gateways work (part 1: `2026-10-11-gateways-control-edge-design.md`).
It replaces per-member server grants (`user_servers`) with teams and an
allow-list of tools per team and gateway. Part 3 (personal vs shared identity
per gateway-server connection) gets its own spec.

---

## 0. Agreed requirements

From the conversation:

- **Allow-list only, selected tools only.** A policy names exact tools
  (`shop1` → `list_orders`, `get_order`). No deny rules, no "all tools on this
  server" wildcard: a tool an upstream adds later stays hidden until allowed.
- **Rules:**

| Situation | Behavior |
|---|---|
| A tool is explicitly allowed | Permitted, if its server is attached to the gateway and enabled, and other checks (key, rate limit) pass |
| A tool has no allow rule | Denied by default |
| A member is in several teams | Union of their teams' allowed tools |
| A member is in no team | No tool access |
| An admin uses a gateway | Every tool on enabled servers attached to that gateway |
| A client calls a hidden tool by hand | Refused, audited as denied |
| A server is detached from a gateway | All its tools denied through that gateway, whatever the policies say |

- **The dashboard enforces the same policy as MCP clients.** Its Tools page and
  Chat run against a chosen gateway, so opening the dashboard never gives more
  than Claude would get through that gateway.
- **Only admins manage** teams, membership and policies. Members see their teams
  and the tools they end up with.
- **Storage:** one row per allowed tool, read fresh on every request, so a change
  applies on the next call on every pod.

Decided in this spec (not stated by the user):

- Admins in the dashboard also pick a gateway: there is no unfiltered mode, and
  every audited call names a gateway.
- A hidden tool's refusal is the existing "Unknown tool" message: it does not
  reveal that the tool exists.
- `user_servers` is dropped. Members on the running install lose their access
  until an admin puts them in a team (the install is one day old).

## 1. Data model

```sql
CREATE TABLE IF NOT EXISTS teams (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name       TEXT NOT NULL UNIQUE,          -- 1-40 characters
    created_at DOUBLE PRECISION NOT NULL
);
CREATE TABLE IF NOT EXISTS team_members (
    team_id BIGINT NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    PRIMARY KEY (team_id, user_id)
);
-- One row per allowed tool. Deleting a team, gateway or server removes its rows.
CREATE TABLE IF NOT EXISTS team_tools (
    team_id    BIGINT NOT NULL REFERENCES teams(id)    ON DELETE CASCADE,
    gateway_id BIGINT NOT NULL REFERENCES gateways(id) ON DELETE CASCADE,
    server_id  BIGINT NOT NULL REFERENCES servers(id)  ON DELETE CASCADE,
    tool       TEXT NOT NULL,                 -- upstream tool name, e.g. list_orders
    PRIMARY KEY (team_id, gateway_id, server_id, tool)
);
DROP TABLE IF EXISTS user_servers;
```

`tool` is the upstream name, not the prefixed `<server>__<tool>`: server names
cannot change, so the pair is stable. If an upstream renames or drops a tool,
its row stays and grants nothing; the dashboard shows it as "no longer offered".

Admins may be added to teams; it changes nothing for them.

## 2. The access rule

One function in `db.py`:

```python
def allowed_tools(db, user, gateway_slug: str) -> dict[int, set[str] | None]:
    """server id -> allowed upstream tool names on this gateway; None = every tool.
    Only enabled servers attached to the gateway appear at all."""
```

- **Admin:** `{server_id: None}` for every enabled server attached to the gateway.
- **Member:** one query joining `team_members`, `team_tools`, `gateway_servers`
  and `servers` (enabled) for this gateway: the union over the member's teams.
  No teams, an empty dict.

`Upstreams.list_tools(user, gateway_slug)` and
`Upstreams.call_tool(user, gateway_slug, name, arguments)` take the gateway per
call (instead of `Upstreams(gateway_slug=...)`), and use `allowed_tools` in place
of both `granted_server_ids` and the attachment filter:

- list: a tool is shown when its server is a key and the tool is in the set
  (or the set is `None`).
- call: anything else is `Unknown tool '<name>'`, audited with `ok=0` and the
  gateway, never forwarded. Rate limit and the disabled-server message keep
  their current order.

An edge passes its own slug. The control plane's health loop keeps checking
every server (Servers page); an edge's loop keeps checking only its attached
servers.

## 3. API (control plane)

| Endpoint | Who | Notes |
|---|---|---|
| `GET /api/teams` | logged in | admin: every team; member: their own. Each: `id, name, members: [{id, username}], policies: {<gateway slug>: [{server_id, server, tool}]}` |
| `POST /api/teams` `{name}` | admin | 201; duplicate name 409 |
| `DELETE /api/teams/{id}` | admin | |
| `PUT /api/teams/{id}/members` `{user_ids}` | admin | replaces the set; unknown user 400 |
| `PUT /api/teams/{id}/gateways/{slug}/tools` `{tools: [{server_id, tool}]}` | admin | replaces this team's policy on this gateway. Each server must be attached to the gateway (400 otherwise); `tool` is a non-empty string up to 128 characters. Not checked against the upstream's current list, so a server that is down can still be configured |
| `GET /api/tools?gateway=<slug>` | logged in | what an MCP client on that gateway gets |
| `POST /api/tools/call` `{gateway, name, arguments}` | logged in | |
| `POST /api/chat` `{gateway, messages}` | logged in | tools and calls under that gateway's policy |

`gateway` missing → 400; unknown → 404 (all three endpoints).

Removed: `PUT /api/users/{id}/servers`, `server_ids` on `POST /api/users` and
in `GET /api/users` (which gains `teams: [name]`).

`GET /api/servers` for members: the servers they have at least one allowed tool
on, through any gateway. Admins: unchanged.

## 4. Dashboard

- **Teams page** (admin): create and delete teams; tick members; for each
  gateway, a tool picker grouped by the servers attached to it, listing each
  server's current tools (from its health status) with a checkbox, plus any
  saved tool the server no longer offers, marked "no longer offered" so it can
  be unticked. Save writes one `PUT .../tools` per gateway changed.
- **Members page:** the Access column and editor go; a Teams column shows each
  user's teams (read-only, edited on the Teams page).
- **Tools and Chat:** a gateway selector at the top (first gateway by default,
  last choice remembered in `localStorage`); every list and call sends it.
  No gateways yet: a note pointing at the Gateways page.
- **Members** see a read-only Teams view: their teams and, per gateway, their
  tools.

## 5. Testing

Gateway tests (Postgres, as in part 1):

- `allowed_tools`: admin gets every attached enabled server; member union over
  two teams; no team → empty; detached server drops out even with rows; disabled
  server drops out.
- Edge end to end: two members in different teams on one gateway list different
  tools; a hand-typed call to a tool outside the policy is refused, audited
  `ok=0` with the gateway, and never reaches the upstream; adding the tool to the
  team applies on the next request; detaching the server removes it whatever
  the policy.
- Teams API: admin-only writes (member 403); policy for an unattached server
  400; deleting a gateway, server or team removes its rows.
- Dashboard endpoints: `/api/tools`, `/api/tools/call` and `/api/chat` require
  `gateway` and enforce the same set as the edge.
- Existing tests that used `server_ids` grants move to teams.

Dashboard: `npm run build`; checked by hand on the cluster.

## 6. Out of scope

- Team managers (non-admin editing).
- Per-team rate limits (the per-user limit stays).
