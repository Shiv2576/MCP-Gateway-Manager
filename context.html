1. The Goal

A WooCommerce store environment on Kubernetes plus a team MCP gateway. Admins register upstream MCP servers using Streamable HTTP, optionally attach static credentials, and expose all enabled upstream tools through one MCP endpoint.

One MCP endpoint

Clients connect to the gateway instead of individual upstreams.

Safe routing

Tool calls are routed to the correct upstream with timeouts and audit logging.

Credential isolation

Upstream credentials remain server-side and never reach browsers or MCP clients.

Team access

Admins manage users, API keys, server grants and the audit log.

Chat agent

The dashboard can use gateway tools as the logged-in user.

Multi-store

Admins can provision up to three WooCommerce stores from templates.

4. Components

4.1 Store

  • Bitnami WordPress + MariaDB with persistence and per-store Ingress.
  • Setup Job installs WooCommerce, configures permalinks/COD, registers the MCP key and seeds products/orders.
  • Templates: catalog-a, catalog-b, blank.
  • Operator-created stores use a normal setup Job so it disappears with the namespace.

4.2 woo-mcp

Python MCP server using the WooCommerce REST API. Requests are OAuth 1.0a signed against the public store URL while traffic is sent to the internal Kubernetes Service.

Tool Purpose
list_products Newest-first products, optional name search, pagination and limit.
create_product Create and publish a simple product.
delete_product Move a product to trash.
list_orders List orders by date and optional status.
get_order Get one order with items, payment method and destination.
update_order_status Change an order status.

Order data is minimized: no customer email, phone or street address is returned.

4.3 Gateway

Starlette + MCP SDK with SQLite stored at /data/gateway.db on a persistent PVC.

Table Purpose
users Users, scrypt password hashes and roles.
sessions Hashed session tokens with 12-hour expiry.
api_keys Hashed MCP keys, owner and revocation state.
servers Upstream URL, credential metadata/value and enabled flag.
user_servers Member-to-server grants.
audit_log Time, user, tool, server, success, duration and error.

Upstream manager

  • Refreshes enabled upstream tools every 30 seconds in parallel.
  • Each listing has a 5-second timeout and is stored in memory.
  • MCP tool listing never waits for an upstream.
  • Individual calls have a 10-second hard timeout.
  • All calls pass through one path: rate limit → grant → enabled check → upstream call → audit.
  • Disabling a server hides its tools immediately; revoked API keys fail on the next call.

Tool collision scheme

Every tool is exposed as <server>__<tool>. For example: notes__list, fx__list and basic1__list_orders. Server names cannot contain underscores, so the first double underscore is unambiguous.

Authentication and credentials

  • Browser login creates an HttpOnly, SameSite=Strict session cookie.
  • MCP clients authenticate with a bearer API key shown only once.
  • Upstream credentials support a custom header or bearer token.
  • The gateway API exposes only credential metadata such as header name and whether a credential exists.
  • Client-supplied headers are not forwarded upstream.

Roles

Role Access
Admin Servers, users, all keys, audit log, stores and every tool.
Member Only granted servers and the member's own keys.

4.4 Demo MCP servers

notes provides save_note and list, using an X-API-Key credential. fx provides convert and list, using a bearer credential. Both intentionally expose list to demonstrate collision handling.

4.5 Dashboard

React 19 + Vite 7 served by nginx. Main pages:

  • Servers — health, credentials, add/edit/disable/remove and tool lists.
  • Tools — typed input forms generated from MCP schemas.
  • Stores — provisioning, status and deletion.
  • Chat — LLM agent using gateway tools as the logged-in user.
  • API keys — create, display once, revoke.
  • Users — admin/member creation and server access.
  • Audit log — latest calls with automatic refresh.

4.6 Chat agent

  1. Browser sends the current conversation; nothing is stored server-side.
  2. Gateway authenticates the user and validates the message history.
  3. Only enabled and granted tools are offered to the model.
  4. At most six model/tool rounds are executed.
  5. Every tool call uses the same gateway routing, timeout, rate-limit and audit path.
  6. Model/provider errors return a concise gateway error.
The “confirm before changes” behavior is currently a system-prompt rule rather than a hard server-side authorization requirement.

4.7 Member access

Members start with no server access. Admins grant servers explicitly. Enforcement happens in both tool listing and execution, and therefore applies consistently to MCP clients, the Tools page and the chat agent.

7. Problems Found and Resolved

Problem Cause Resolution
WooCommerce 401 Secret contained a stale key. Synced the Secret and restarted woo-mcp.
Browser /mcp authentication error Expected MCP-client-only endpoint. Use the dashboard for human interaction.
Claude Code connection refused Wrong registered URL. Use gateway.localhost/mcp.
Claude called direct woo Old direct woo connection remained. Remove the direct connection.
Timeout wording HTTP client timeout fired before the gateway timeout. Normalized timeout handling and messages.
Operator import/user errors Kopf script path and image UID had no passwd entry. Set PYTHONPATH=/srv and USER=store-operator.
Store deletes hung Single node reached memory pressure. Added low-priority store-workload PriorityClass.
Old store PVC stuck terminating Helm hook Job survived uninstall and held the PVC. Deleted the Job; operator uses setup.hook=false.
Tools needed raw JSON No schema-driven UI. Typed form generated from MCP input schemas.
delete_product reports publish WooCommerce returns the object state from before trashing. Open: one-line response-status fix.

8. Known Limits

Local capacity

A single k3d node comfortably fits about two stores alongside the platform. Three may require more Docker memory.

Single replica

SQLite and in-memory rate limiting currently require one gateway replica.

Credential storage

Upstream credentials are stored in plaintext SQLite. Encryption is planned.

SSRF

No server-URL SSRF validation exists yet.

Login protection

No login rate limiting is implemented.

Chat confirmation

Mutation confirmation is prompt-level, not a server-enforced policy.

Member granularity

Access is per server, not per tool.

Chat history

Conversation history exists only in the browser tab and is not persisted.

Tools UI

Nested objects and multi-type fields fall back to JSON input.

Operator permissions

ClusterRole is broad because Helm needs access to resources in new namespaces.

Store egress policy contains cluster-specific pod/service CIDRs. Those values must be adjusted for another Kubernetes cluster.
